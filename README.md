# Сервис бронирования переговорок

## Запуск

```bash
docker compose up -d --build
```

Снаружи сервис открыт на **http://localhost:8080**. Я использовал **nginx** как reverse proxy, чтобы с одного порта проксировать и API, и Swagger в разные контейнеры и не делать отдельно CORS для Swagger.

Переменные окружения см. .env.example. Для локального запуска приложения без Docker нужен доступный PostgreSQL и строка `DATABASE_URL`.

## Как появляются слоты

1. При создании расписания сразу создаются слоты на неделю вперёд.
2. Затем фоновый воркер `slotworker` каждый день в 03:00 UTC создаёт новые слоты на седьмой день: день закончился, на ближайшие шесть дней слоты уже есть, воркер доделывает слоты на седьмой день.
3. По запросу `GET /rooms/{roomId}/slots/list` на дату, не входящую в семидневное окно, идёт ленивая генерация.

**Обоснование.** В ТЗ указано, что запросы слотов в основном укладываются в **ближайшие 7 дней** — поэтому основной объём 
создаётся при создании расписания и доделывается воркером: самый частый сценарий — чтение из БД без тяжёлой генерации в запросе. 
Раз в сутки окно сдвигается вместе с датой. В 0.01% случаев приходится догенерировать слоты во время запроса, что не критично 

## Тестирование

**Юнит-тесты** (без поднятого API, моки):

```bash
docker compose --profile test run --rm unit-tests
```

**Интеграционные тесты** Сценарии сами вызывают API (создание комнаты, расписания, брони, отмена), отдельная подготовка 
данных не требуется; созданные сущности по возможности удаляются.

```bash
docker compose --profile test run --rm integration-tests
```

## Наполнение БД для нагрузки

Скрипт [`scripts/seed.py`](scripts/seed.py) перед вставкой **очищает** таблицы `bookings`, `slots`, `schedules`, `rooms`, `users` и заново наполняет их. Зависимости: `pip install -r scripts/requirements-seed.txt`.

**Значения по умолчанию** (в рамках верхних границ ТЗ: до 50 переговорок, до 1k слотов в день, до 10k пользователей, до 100k броней):

1. **Переговорки — 50.** У первой фиксированный UUID `a0000001-0000-4000-8000-000000000001` (как в `tests/load/load.js`).
2. **Расписания — 50** (по одному на комнату): дни недели 1–7, начало UTC `08:00`, конец времени подбирается под максимальное число слотов на комнату в этот день.
3. **Слоты — 1000** 
4. **Пользователи — 10000:** `seed_N@seed.local`, роль `user`, пароль в БД — заглушка.
5. **Брони — 100000:** до **1000** со статусом **active** (по одной на слот); остальное **cancelled**, пользователи из пула по кругу.


```bash
docker compose --profile seed run --rm seed
```

Либо с хоста при доступном `localhost:5432`: `python scripts/seed.py`.

## Нагрузочное тестирование

Сценарий [**`tests/load/load.js`**](tests/load/load.js) нагружает самый тяжёлый эндпоинт по ТЗ — **`GET /rooms/{roomId}/slots/list`**. 
Используется фиксированная интенсивность (около 100 запросов в секунду), в `options.thresholds` заданы ограничения по доле ошибок и по **p(95)** времени ответа. 
Перед прогоном нужны поднятый стек и выполненный сид.

Пример запуска **k6 в контейнере**, если приложение слушает на хосте `8080` (Docker Desktop, Windows):

```bash
docker run --rm -i -v "${PWD}/tests/load:/scripts:ro" -e BASE_URL=http://host.docker.internal:8080 grafana/k6:0.57.0 run /scripts/load.js
```

## Ссылка на конференцию (мок Conference Service)

В **`POST /bookings/create`** есть необязательное поле **`createConferenceLink`**. Если оно `true`, перед сохранением брони 
вызывается внешний сервис конференций. Реального сервиса нет — используется мок [`internal/conference`](internal/conference/conference.go): 
он возвращает стабильную тестовую ссылку вида `https://mock-conference.invalid/join/{slotId}/{userId}` (или ошибку / пустую строку в зависимости от настроек).

**Порядок операций**

1. Проверка слота и того, что он в будущем.
2. Если нужна конференция — запрос к моку в отдельном контексте с **таймаутом** (`CONFERENCE_SERVICE_TIMEOUT_MS`, по умолчанию 3000 ms). 
Только после успешного ответа с непустой ссылкой идёт вставка брони в БД.
3. Если вставка брони не удалась (например, слот уже занят — конфликт), вызывается **`CancelConferenceLink`** у того же 
мока, чтобы не оставлять «висящую» конференцию без брони в нашей системе (компенсация), считается, что если этот запрос вернул ошибку, то
проблема требует ручного решения.

**Поведение при сбоях (как смоделировано)**

1. **Мок недоступен / вернул ошибку / пустая ссылка** — бронь **не создаётся**, клиент получает **503** с кодом `CONFERENCE_UNAVAILABLE` (конференция сейчас недоступна).
2. **Таймаут или отмена контекста** во время вызова мока — то же: **503** `CONFERENCE_UNAVAILABLE` (внешний сервис не ответил вовремя).
3. **Ошибка после успешного ответа мока** — если упала только запись в БД с конфликтом по слоту, ссылка отменяется через 
`CancelConferenceLink`; клиент получает **409** (слот занят), а не «полуудачную» бронь со ссылкой.
